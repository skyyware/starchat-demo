# Maintain the public knowledge snapshot

stage.dev owns the public guide content. This installation contains a reviewed
snapshot for retrieval, recorded in `knowledge/sources.json`. Each manifest entry
names the public website page, source document and body hashes. The underlying
article preserves its own package version and original evidence links.
Each snapshot also offers the corresponding website guide as an answer link;
adding that destination does not change the reviewed body or upstream evidence.

When an article, package contract or relevant fact changes, inspect the public
source and affected behavior, then update the corresponding Markdown here.
Keep the source URL, reviewed version and dates accurate. Refresh hashes only
after reviewing meaning. Run `composer check`, rebuild the index and inspect a
real answer that depends on the change. A passing hash or index is not an
editorial review. Do not perform date-only refreshes.

The chat never reads the website's private CMS. Do not copy drafts, revision
history or another installation's corpus. No runtime crawler, Markdown mount,
watcher or scheduled maintenance job is required. Shared design updates are
independent of this deliberate knowledge review.

The 31 October 2026 snapshot covers Stage 0.2.0, CMS 0.5.4 and Starchat 0.12.0.
It explains constructor-owned request headers and both supported CMS framework
series. Filled asset buttons sit below up to four questions,
with an independent limit of four controls. The groups never fill or displace
each other. Extra formats page only within the action area. Its localized
heading is available to screen readers, without visible text. The buttons wrap
to fit their labels and use regular text without decorative icons. Questions retain
their borderless text-link styling. The enabled reset icon is the exception:
**New conversation** has a plus and label on desktop and an accessible 44px icon
button on mobile. Short labels stay on one line, while clicks
submit the full suggested reply. Suggestion labels and submitted replies omit trailing
full stops, including restored suggestions. Internal punctuation and question
marks remain. The legal footer uses smaller 13px text. Only a click starts creation.
Answers and preparation use the same three animated dots and short status line,
then the result appears in the conversation. Ready projects use a star
icon, four-word function description and reduced-motion-aware entrance.
Full project details remain in README and PROJECT inside the ZIP. This demo
enables project ZIPs only; other asset types remain disabled.
Downloads use a contrasting fill. Manual retry aligns with its message.
Ready cards hide creation actions they already cover and preceding questions for
the current answer. The composer remains available; failures retain questions
and manual retry.
A PDF with an email card also covers email creation. Other formats and later
answers remain eligible. Email cards have no preview disclosure; telephone
checklists remain expandable. Contact cards retain icon, title and button without
a descriptive line; project captions remain. Reloading creates nothing automatically.

The answer API guide describes optional `suggestion_labels` and reviewed
`contacts`, including their limits, compatibility and local-midnight expiry.
Old answers without contact metadata offer no contextual email or telephone
action. Configured primary email recipients retain their in-scope behavior.
Known phone contacts use direct `tel:` buttons without generation.

The building guide distinguishes this installation's required Stage application
from the engine's optional, technology-neutral project capability. Starter and
custom exports use a verified compatible Stage 0.2 release and supported PHP 8
version, including revisions. The versioned
installation policy validates files before packaging; independent review checks
that Stage routes implement the requested function. Old browser files remain
revision input but need a new creation click before becoming a current export.

Idea discovery starts with an everyday problem and one useful workflow. Only
an explicit framework or runnable-example request offers the configured starter.
Policy `stage-web-v3` also requires responsive interfaces, readable type, labeled
inputs, validation and the agreed create, edit and delete flows for human-facing
projects. API-only requests remain APIs. Generation and independent review do
not establish execution or visual quality; downloaded applications still need
their own checks.

The project-environment guide explains official release checks on the creation
day, compatible defaults and supported explicit version choices. Preparation adds
the dependency lock and `docs/technology.json` before policy and independent
review. It reserves space for those files and the agent handoff within the final
32 KiB limit. Missing current evidence or unverified dependencies cannot produce
a ready export. Generated code is never executed by the service. Local CSS and
scripts need fixed Stage routes and checks for successful responses and content
types through the canonical router.

Ordinary source selection, answers and review use Default service. Asset creation
and review use the fastest profile advertised by the configured model catalogue.
An account change requires fresh capability evidence. The guides retire the global
service-tier setting and do not promise a fixed response time or infer entitlement
from an older catalogue.

Project generation allows 120 seconds, each review 25 seconds, and the shared
budget is 150 seconds. The browser allows 155 seconds; building hosts need at
least 165 seconds at the proxy and worker. Ordinary chat limits are unchanged.
